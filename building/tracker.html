A tracker app

Why

I wanted to find out whether I could build something I would actually use. A thing I open every day and would be annoyed by if it were bad. It tracks a process I had to run carefully anyway, so the build had a real user with real opinions, and that user was me.

What

A local-first web app. A pipeline board, AI-assisted intake with fit scoring, and documents drafted from one maintained profile. Everything lives in one JSON file on my machine, and nothing touches a server.

I build by directing AI development tools.

Decisions

  • Local-first, no server

    One JSON file plus a folder of uploads. For a tool with one user holding their own private data, a backend would have been cost, a security surface, and something else to maintain, in exchange for nothing I needed. Backing it up means copying a folder.

  • I reversed the no-API decision

    The first version deliberately had no API key. The app assembled the prompt, I ran it myself, and I pasted the result back. Free, same model, same quality, and I argued that a few seconds of copying was the whole cost.

    I had the cost wrong. It was not the copying. It was that I had made myself the transport layer for my own tool, and that the app could not check its own work. It asked for structured data in prose and then dug the answer back out of the reply by pattern matching, which fails quietly and leaves the app with nothing useful to say. Now the shape is declared once and enforced by the API, so that whole class of failure is gone and the file that scraped replies is deleted.

  • What is true and what to act on are two questions

    Items now count how long they have been quiet, and past a threshold the app closes them for me. That rule is deliberately narrow. It cannot touch something I never sent, it cannot touch one that finished well, and it skips anything I reopened by hand, because reopening is me saying I already know it is quiet and I want it left alone. The board still shows those as quiet, because they are. One function answers whether something has gone cold and a separate one answers whether the app is allowed to act on it. Keeping those apart is what stops it from tidying away something I still care about.

  • Scores expire when the criteria change

    The idea I care about most here. Everything gets a fit score, but a score is only as good as the criteria it was judged against. So the app remembers what the criteria were when each score was written, and when I change what I am looking for, every score judged under the old ones is flagged stale and can be redone in a batch. Without that, old numbers sit there looking current and quietly lie to me.

  • Nothing scores itself

    Re-scoring is a button. It never runs on save. I wanted the machine's judgment to be something I asked for, not something that turned up while I was busy and got mistaken for my own.

Log

  • Sep 9

    Reversed the no-API decision and wired the app straight into the model, which removed six copy-and-paste flows and the file whose only job was scraping replies for structured data.

    The smaller thing taught me more. Items close themselves once they have been quiet long enough, and my first version reset the clock whenever anything moved. Then I moved one back out of closed and it told me the wait had started today. Moving something back is me undoing a decision, not the other side getting in touch. The clock resets only on something real now. I found it because I use the thing on my own data.
